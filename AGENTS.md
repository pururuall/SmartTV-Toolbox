# AGENTS.md — SmartTV_Toolbox

Инструкции и правила поведения для ИИ-агентов, работающих с проектом `SmartTV_Toolbox`.
Основаны на инженерных принципах Андрея Карпатого (**Andrej Karpathy Guidelines**): *Think Before Coding*, *Simplicity First*, *Surgical Changes* и *Goal-Driven Execution*.

---

## 1. Архитектура и структура проекта

Проект представляет собой Windows-приложение для управления Android TV / YaOS через ADB (Python + PyWebView + HTML/JS).

* **Точки входа:** `main_webview.py` (основное окно WebView), `gui_app.py` (GUI-панель), `server.py` (локальный сервер).
* **Бизнес-логика:** `tv_manager.py` (ADB-команды, профили debloat, управление пакетами). При рефакторинге логика выносится в пакет `core/`.
* **Пользовательский интерфейс:** `app_ui.html` — **единственный источник правды** для веб-интерфейса. Никаких клонов (`Instruction.html`, `START_HERE.html` и т.д.).
* **Приложения (APKs):** каталог `apps/` со структурированными подпапками (`launchers/`, `media/`, `youtube/`). **Один файл APK — в одном месте.**
* **Утилиты:** `platform-tools/` (локальный бинарник `adb.exe`).
* **Временные файлы:** папка `.scratch/` (не коммитится).
* **Сборка:** папка `dist/` (не коммитится).

---

## 2. Ключевые правила (Karpathy Guidelines)

### 2.1. Surgical Changes (Хирургическая чистота)
* **Категорический запрет на коммит бинарников:** никогда не добавлять и не коммитить в Git файлы `*.exe` (включая `SmartTV_Control.exe`), `build/`, `dist/`, `*.spec` и временные дампы. Бинарные сборки живут только локально или в релизах GitHub.
* **Чистый корень репозитория:** запрещено создавать временные тестовые скрипты (`find_*.py`, `check_*.js`, `dump_*.bat`) и логи прямо в корне проекта. Все разовые эксперименты и исследования проводятся строго внутри `.scratch/`.
* **Убирай за собой:** созданные агентом временные файлы и дампы должны быть удалены или перенесены в `.scratch/` до завершения задачи.
* **Не трогай чужое:** не форматируй соседний рабочий код, не меняй отступы в несвязанных функциях, не удаляй существующие комментарии.

### 2.2. Simplicity First (Простота и YAGNI)
* **Единый источник правды:** не дублировать код и ассеты. Если нужен интерфейс — править только `app_ui.html`. Если нужен APK — хранить его ровно в одной подпапке `apps/`.
* **Модульность вместо монолитов:** функции и методы должны быть компактными. Не допускать раздувания файлов свыше 300–400 строк; сложные участки декомпозировать на модули с понятной ответственностью.
* **Минимум магии:** решать задачу самым простым и очевидным кодом без спекулятивных абстракций «на будущее».

### 2.3. Goal-Driven Execution (Проверка перед сдачей)
* **Критерий готовности:** перед коммитом или отчетом агент обязан запустить проверку:
  1. Синтаксическая валидация Python: `python -m py_compile <измененные_файлы>`
  2. Запуск тестов (smoke test): `python -m unittest discover tests` (или `pytest`)
  3. Проверка статуса Git: `git status` должен показывать только ожидаемые целевые изменения.
* **Атомарные коммиты:** разбивать крупные задачи на небольшие верифицируемые шаги с осмысленными сообщениями.

### 2.4. Think Before Coding (Осознанность и согласование)
* **Явные допущения:** не додумывать за пользователя поведение неочевидных функций. Если есть развилка — задать вопрос или предложить варианты с компромиссами (tradeoffs).
* **Предупреждение о деструктивных действиях:** при операциях очистки (удаление дублей APK, чистка веток Git, перезапись профилей debloat) всегда озвучивать список удаляемых файлов перед исполнением.

---

## 3. Чек-лист для агента перед завершением любой задачи

- [ ] Все временные файлы удалены или изолированы в `.scratch/`.
- [ ] Никакие `.exe`, `.log`, `.tmp` не попали в `git status`.
- [ ] Измененный Python-код компилируется без синтаксических ошибок (`py_compile`).
- [ ] Приложение запускается без ошибок импорта.
- [ ] Diff содержит только минимально необходимые изменения по задаче.
